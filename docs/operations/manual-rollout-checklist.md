# Manual rollout checklist

**Baseline audited:** `0e5070f5918fa9ab9b89e61b2cb5b73e1f99cd1d` (`main`, 18 November 2026). **Status:** local changes only. No production settings, secrets, databases, or deployments were changed. Nothing was pushed. Check off an item only after its owner records the evidence below against the intended revision.

## Before landing or enabling production traffic

- [ ] **Repository admin — protect `main`.** At audit time no branch protection or repository ruleset was returned for `main`. Require PR review and the correct always-reported landing/verification checks for the tested revision; block force-pushes, deletion, and direct writes or bypasses not explicitly required by policy. Verify local, Render and GitHub fallback lanes against [the landing contract](../PR_TO_PRODUCTION_LIFECYCLE.md). **Evidence:** ruleset/protection link; required check names and app identities; a denied bypass and a normal reviewed PR run. A green non-required job is not enforcement.
- [ ] **Release owner + GitHub admin — restrict production deploys to protected `main`.** Verify the `production` environment retains required reviewers, prohibits self-approval, and allows only the intended deployment branch. The current protected-PR **Owner Review** job also uses that environment: configure and verify a separate reviewer-protected PR environment **before** moving that job or restricting `production`, so protected PRs neither bypass review nor deadlock. Audit scheduled repair workflows and separate production mutation credentials from CI runner/read-only credentials before moving secrets into environment scope. **Evidence:** redacted settings plus main and non-main dispatch outcomes, and a protected PR explicitly waiting for its reviewer.
- [ ] **CI owner — restore or formally retire the suspended Render CI runner.** A suspended deployment is `not_run`, and a matching provider-only record for a runner without `/release` is `metadata_only`. Neither proves that a test ran. Confirm runner ownership, health and fallback eligibility. Dispatch [Full Test Battery](../../.github/workflows/full-test-suite.yml) on the candidate SHA; review collection failures, skips and test artifacts, and verify the Tower build, annotation, visibility and access checks. The [audited main run](https://github.com/Supremeai-bd/supremeai/actions/runs/44452288451) did not demonstrate a full battery or live rollout. **Evidence:** exact-SHA runs and the fallback verdict when the primary runner is unavailable.
- [ ] **Gateway and Vault owners — approve and stage zero-cost API routes.** Existing keys, a model named `free`, and HTTP 200 do not establish entitlement. Follow the [Gateway secrets contract](../../gateway/SECRETS_MODEL.md): check account-level billing restrictions, allowed endpoint/model/modalities, quota and expiry for each credential; install `SUPREMEAI_FREE_ROUTE_POLICY` privately; rotate the approval together with the key. For OpenRouter and Kilo confirm fresh same-credential `/models` pricing for the exact concrete slug. Verify the relay's real upstream, access, data handling and cost separately. **Evidence:** redacted policy/entitlement review, no-billing control, approved JSON/SSE and negative/rotation tests in staging. Do not run inference probes against unproven accounts.
- [ ] **Service owners — build and smoke the actual artifacts.** Build Gateway, Core, Browser, Worker, Tiny Brain and Tower where registered, from their declared build contexts and with the intended runtime versions. Test the exact image digests in staging. Check aliases, auth, early/late SSE failures and disconnect cleanup, `/readyz` vs `/health`, and Tiny Brain short/long context routing. Exercise valid and denied MCP calls. **Evidence:** digests, runtime `/release` output and redacted smoke results. Local source/COPY-layout tests are not Docker builds.
- [ ] **DB owner + Core — verify staging data boundaries.** Confirm the intended Supabase project/ref, migration version, vector dimension, query/update RLS and RPC execute grants. Verify `match_ai_memories` returns `user_id`, `session_id`, and score, and matches the supported schema with owner and session filters. Test different owners sharing a session identifier, stale/missing RPC, Redis outage and multi-worker cache invalidation (including a worker disconnected during the purge). Confirm whether owner-wide memory is intended across workspaces; do not backfill ambiguous ownership or restore legacy response/checkpoint keys. **Evidence:** migration/readiness report and positive/negative test receipts using fixtures in the authorized staging project.
- [ ] **Release owner — attest exact revision and rehearse rollback.** For each affected service reconcile registry, service ID, intended SHA, triggered deploy ID, Render `live` commit and runtime `/release` SHA. Run canaries separately. Diagnose any `UNREGISTERED`, missing, stale, `not_run`, or `metadata_only` evidence; do not accept it as production verification. Rehearse [rollback](../runbooks/rollback.md) to a schema-compatible ancestor with the on-call owner and record the restore time. The current `all` option covers Gateway, Browser and Tower only; document rollback for Core, Worker, Tiny Brain and affected edge services separately. **Evidence:** deploy IDs, SHA equality, canary results, and linked rollback run. See the [root release gate](root-release-gate.md) for the remaining sign-off requirements.

## Product decisions and caller verification

- [ ] **Core + Worker owners — prove a real job.** Identify the producer of `ecosystem:tasks` and the consumer of `ecosystem:results`. The tracked Worker `_execute()` remains a placeholder. Either prove an actual result plus durable receipt, retry, cancellation and drain/replay, or stop advertising unsupported execution after caller review. **Evidence:** producer → queue → execution trace or approved retirement plan.
- [ ] **Browser owner — confirm the supported capability.** The current build declares a relay, not the separately implemented `/scrape`, `/browse`, or `/recipe` features. Confirm the relay-only contract or name an authorized caller before packaging an isolated browser capability. **Evidence:** supported routes on a built image, denial and dependency-failure checks, and dependency/permission review.
- [ ] **Integration owners — reconcile webhook and compatibility callers.** Select one authenticated sender, payload, persistence path and replay receipt for the two Core `POST /api/ci/webhook` registrations. Confirm an actual Telegram bot/caller before enabling inbound strategy processing, and whether V0 or legacy Gateway/factory aliases are supported. Gateway's outbound management is metadata only; Core's legacy outbound paths return unavailable. Do not re-enable delivery until a tenant-owned sender, destination restrictions, message signing and delivery receipts exist. **Evidence:** redacted end-to-end sender/receiver or migration receipts, including negative authorization tests.
- [ ] **Product + Core/Gateway maintainers — verify transcript and older learning contracts separately.** Exercise send, reopen, find and export in the actual supported client. Decide whether any internal, non-private learning workflow needs a scoped replacement for the retired serving-path response reuse/learning hooks. Reconcile the old `save_healing_event` tests with the supported AutoHealer persistence contract before claiming a full battery pass. **Evidence:** traceable client/storage receipts and updated support/test decisions, not UI stubs or an import-only smoke test.
- [ ] **Gateway + security — confirm client credential scope.** API/relay model aliases constrain per-request routing; they are not six separately scoped client credentials. Confirm the supported grant model and prove allowed/denied use on the built application before introducing route-scoped keys. Keep provider entitlement separate. **Evidence:** caller inventory and a tested token migration/rotation plan if needed.
