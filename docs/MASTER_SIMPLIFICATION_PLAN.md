# SupremeAI Master Simplification & Quality Plan

**Status:** Final implementation roadmap from the two simplification plans. It sets scope and order, not approval to deploy, remove a supported surface, or change production data.

**Implementation baseline:** `aa11e0baf086ce0a4e4b7c16a86e23816c24c8b9` · 18 November 2026.

**Intended decision owners:** Product for supported journeys; domain maintainers for behavior; operations/security for release and trust boundaries.

## 1. Final decision

Use **this document** to decide what to implement and in what order. Keep the [Project Simplification Plan (বাংলা)](PROJECT_SIMPLIFICATION_MASTER_PLAN.md) as the dated audit: inventory, original findings, and per-component detail. Section 5 below supersedes its draft backlog. There is no third plan and no parallel backlog to maintain.

**Keep the reason, not necessarily the mechanism.** The repository most clearly supports two intentions: **one stable way to use AI across model providers** and **one controlled way for agents to do verifiable work**. Core adds a distinct proposition: workspace-, tenant-, and task-aware behavior beyond a plain model call. Low cost, availability and safety are constraints on these outcomes—not reasons to keep every service, retry, mirror, or guard. The owner still needs to confirm which journeys are actively supported.

What exists is not uniformly at the same stage. There is a Gateway selected by Docker and a different app commonly used for tests; a Worker entrypoint can produce a completion record without a task result; a packaged Browser layout can answer health checks without mounting browser capabilities; and “Tiny Brain” covers policy rules, probes, and experiments, not one verified trained inference service. Those gaps matter more than the file count.

**Target:** Gateway owns the public client contract and provider boundary. Core owns tenant state and product task decisions. Tower owns permissioned MCP tool access and governed repository work. Preserve the Worker or Browser execution boundary where a supported workflow needs it. Keep Tiny Brain, HF/Kaggle and niche capabilities off new default paths until they prove a benefit. These are ownership decisions, not a mandate to combine runtimes or databases.

**Start with M01:** test the exact Gateway app named by the Dockerfile with a controlled provider. M02, the regression fix for the checked-in workflow planner, can run in parallel. An unknown deployment status should block removal, not these local fixes.

## 2. How to read the evidence

- **Documented intent:** a source comment, contract, or design note states the problem it was meant to solve. This is evidence of what was *stated*, not a historical interview or proof that customers use it.
- **Inferred intent:** code, boundaries and tests suggest a reason. Treat it as a hypothesis; use a named caller or user outcome to confirm it. Do not turn a guess into an architecture requirement.
- **What we have:** distinguish **source present**, **build/runtime declared**, **locally reproduced**, and **live/used**. A route decorator, registered tool, successful import, configured URL, and completed user journey are different kinds of evidence. This review did not verify live deployments, traffic, costs, external releases or branch-protection settings.

Current checkout inventory: **4,427 tracked files**, **3,629 Python files**, 2,160 under `core/`, 493 under `gateway/`, 98 under `browser/`, 801 under `scripts/`, and **7 root workflows / 66 declared jobs**. Jobs are event-conditional; this is not an execution count. The [earlier `aa11e0b` repo audit](PROJECT_SIMPLIFICATION_MASTER_PLAN.md) contains the detailed inventory and additional checks from the previous review. The upload's `effb70925` report (4,157 files, 11,933 collected tests, 58 passed/4 failed in its selected run) is historical, supplied evidence. That commit is not available in this shallow checkout; its results were not rerun, and neither ancestry nor a trend can be inferred by subtracting the two sets of counts.

### Why the complexity may have accumulated — hypotheses, not history

1. **Compatibility and deployment split:** reference apps and packaged apps were allowed to diverge, likely to keep more than one caller or build layout working. Check a real client and artifact before merging. Same name or directory is not enough.
2. **Availability and quota pressure:** extra pools, keepwarm, alternate execution and multiple probes all target useful outcomes, but can add retries, idle work and more ways to be “healthy” without doing the job. Keep only lanes with measured gains and approved access.
3. **Incident-by-incident protection:** byte or directory guards try to prevent previous drift; the guard can outlive the migration and check the wrong shape. Preserve the *invariant* (one behavior owner or public boundary), not a copy count. Never make a guard green by deleting an active implementation or importing Core private modules from Gateway.
4. **Experiments crossing into product claims:** a notebook, rules API, status tool, or placeholder worker is a useful intermediate artifact only if it is named honestly. Promote it when it proves a real result, not when a route or feature name appears in a catalog.

| **Inbound webhooks** — accept an authentic event and give it a real outcome | The staged Core app mounts two `POST /api/ci/webhook` handlers: [CI report ingest](../core/api/routes/ci_webhooks.py) first (header secret, stored report) and [dashboard summary ingest](../core/api/routes/ci_dashboard_api.py) second (body secret, in-memory summary). If unsupported, stop advertising delivery and use the agreed deprecation path. | **Context, memory, caching and protections** — reduce cost only while serving the right state | The [context engine](../core/context_engine/engine.py) is used in Core chat; [memory recall](../core/services/memory_service.py) and [SynapticMemory](../core/intelligence/synaptic_memory.py)'s process-local state are not the same storage contract. [App middleware](../core/app_builder.py) attaches request rate limiting and idempotency separately; the [anti-hacking](../core/middleware/anti_hacking.py) and [limiter helper](../core/middleware/rate_limiter.py) filenames are not proof that those classes cover every route. | **M06 affected-release check:** verify cache isolation before enabling shared caching for private responses. Start with exact scoped caching over effective model, context/policy and relevant inputs, or bypass when equivalence is unknown. Keep semantic/prefix caches only with correctness and speed evidence; keep retrieval distinct from caching and preserve actual auth/rate-limit/idempotency coverage. |

The rule generalizes: **fix a verified wrong result, unsafe boundary, missing build dependency or competing owner first; reuse a small adapter that preserves a real contract; retire only after caller and rollback evidence.** Apply the same evidence to a Worker result, a Browser feature mount and Tower permission checks. Don't infer fake behavior from `proxy` in a name, or real behavior from a 200, import, or test count.

### Minimum evidence for keeping or removing a small part

In the relevant PR or existing inventory, write one row: `part → job and beneficiary → reason [documented/inferred/unknown] → actual entrypoint or caller → proof → keep/simplify/isolate/retire → rollback`. Ask **what gets worse for a user or operator if this is removed?** A required recovery or safety feature can justify itself without traffic. Unknown caller or unknown retention is not evidence of non-use.

Keep one authoritative implementation per behavior/trust boundary, not one file for the whole monorepo. Migrate consumers before removing a public route, CLI alias or tool name; agree a compatibility window based on the published contract and actual usage before disabling it. Compare old/new artifacts in authorized staging. Stop or revert a rollout on a failing required contract, tenant/security regression, lost or duplicate job, or a breach of the agreed reliability/cost budget. For stateful changes use compatible versions, drain/backfill/reconcile, and rehearse restore; an old image alone is not a database rollback. Don't weaken required checks, protected-path rules, security scans or rollback gates to meet a simplification target.

### What success means

- **Customer outcome:** a scoped client gets a valid answer or a truthful error; a supported task yields the promised result; an authorized tool call behaves as declared. Compare actual outputs, not number of classes or test passes alone.
- **Reliability and cost:** measure p95 first-token/total latency, error and completion rates, retry/fallback use, queue lag, RSS/cold start, CI wall time and cost per *successful* operation under the same workload. No “zero-cost” or performance guarantee based on comments. Agree budgets after baselining them.
- **Release and data safety:** verify intended/deployed/runtime SHA and required feature/schema state; preserve permission, tenant isolation, migration history, data retention and restore evidence. `not run` is not `healthy` or `passed`.

## 6. Questions that source alone cannot answer

1. **What must a user be able to do today?** Name the highest-value current journey and actual client: API chat/IDE use, a tenant workspace doing a real task, or governed MCP work. More than one may be supported; start with the one customers or operators will notice breaking.
2. **What is really deployed and used?** Ask the owners for the running SHA, service/artifact, a privacy-safe usage or execution record, and authoritative store for Gateway/Core/Worker/Browser/Tower. Which Studio/satellite/edge/client paths still carry traffic or release obligations?
3. **Which duplicates are safety or compatibility boundaries?** Name the consumer and removal window for an old route/tool/runtime. Keep separate domains when permissions, scaling or data retention actually differ.
4. **What earns promotion out of experiment?** For Brain, provider discovery, HF, Kaggle and niche skills, name the permitted data/provider, baseline, measurable benefit, spend/schedule cap and stop decision. Which quality evidence and human approvals are mandatory to release?
