**Status:** Evidence-based baseline and sequenced plan (not yet an implementation approval or a claim that the full system passed).  
**Repository:** `Supremeai-bd/supremeai`  
**Plan owner:** Product/architecture maintainer  
**Reviewed at:** local checkout of `HEAD` (commit `effb70925`), updated 2026-11-18 after comparing the supplied `aa11e0b` audit; the two snapshots are distinct and their counts/results must not be combined.  
**Guiding principle:** one owner and one source of truth per behavior; add no abstraction, guard, compatibility path, or dependency without a demonstrated need. Fix root causes, not symptoms. Remove only after proving the active path and consumers.

## 1. Executive summary
SupremeAI is a broad Python-first monorepo. In this audit's `effb70925` snapshot the prior inventory recorded **4,157 tracked files**, **3,359 Python files**, **2,028 under `core/`**, **226 under `gateway/`**, **72 under `browser/`**, **765 scripts**, **8 root workflows**, and **11,933 collected pytest tests**. The user-supplied audit describes a different snapshot, `aa11e0b`, with **4,427 tracked files**, **3,629 Python files compiled**, **493 `gateway/` files**, **801 `scripts/` files**, **7 workflows**, and different focused test results. These counts and test outcomes are snapshot-specific, not a mergeable baseline. At `effb70925`, a focused regression run recorded four failures; default collection did not prove the suite passed.

The clearest systemic simplification target is **drift caused by multiple owners**, not an instruction to aggressively shrink every directory. Examples observed:

1. `config/service_registry.yaml` describes a canonical service registry, but deploy selectors also encode independent rules in `scripts/ci/plan_render_deploys.py`, `core/config/service_topology.yaml`, and `.github/workflows/unified-pipeline.yml`; the wiring scanner then checks whether some of those copies agree. These files also contain genuinely different contracts (Render runtime metadata vs. cross-platform deployment routing), so establish which fields truly share an owner before consolidating.
2. The repo/documentation simultaneously calls satellite repositories retired and describes active satellite dispatch; retired `studio/` still appears in deployment branches and historic docs. In `render.yaml`, the MCP Tower uses a `rootDir`-relative bootstrap command, while `config/service_registry.yaml` describes a root-style entrypoint. Decide the actual topology and generate or validate all views against that decision.
3. Gateway has two substantial app surfaces: the FastAPI app factory in `gateway/main.py` and a separately constructed, much larger global app in `gateway/service/app.py`; deploy uses the latter. Legacy entrypoints, tests and CI references make it unsafe to delete either by assumption. Select one production owner, explicitly classify the other as a required compatibility surface or retire it in stages, and preserve contract tests.
4. Root pytest scanning is broad across `tests`, `core/tests` and `gateway/tests`; 213 root-level test modules alone sit in addition to nested tests and subsystem suites. The Node control tower's `package.json` declares a very long, overlapping set of individually named tests, `test:unified`, and `test:tower-ci`. Make one deterministic test inventory per subsystem and ensure CI invokes it rather than repeating lists.
5. `docs/CODEBASE_AUDIT_CHECKLIST.md`, `docs/PIPELINE_ARCHITECTURE_AND_EXECUTION_SSOT.md`, `README.md`, and `ECOSYSTEM_MAP.md` contain directions, lifecycle descriptions or architecture facts that are visibly stale relative to current tracked paths, workflows or policies. Documentation that contradicts the executable tree is a safety defect.

**First principles:** keep API and auth invariants, schemas, migration history, secret boundaries, negative tests, and observable failure behavior. Simplify speculative/duplicate scaffolding, stale instructions, overlapping registries, oversized orchestration, duplicate utilities, and always-on dependencies only after proving they are unused on the production path.

## 3. Target architecture and operating rules
### 3.1 Non-negotiable SSOT boundaries
| Concern | Canonical owner | Other representations |
|---|---|---|
| Public HTTP/MCP interfaces | `api-schemas/` and OpenAPI contract fixtures | Generated models and route implementation validated against the schema; do not manually fork contract definitions. |
| Service runtime identity (name, image/entrypoint, port, health, required env names) | Choose one versioned service registry | `render.yaml`, deploy matrix and documentation are generated or drift-checked views; secrets remain in a vault, never in registry values. |
| Cross-platform deploy selection | Choose one deploy-topology/routing config; determine whether `core/config/service_topology.yaml` replaces or complements `config/service_registry.yaml` | One selector reads it. CI/deployment actions consume its output; no parallel watch-path dictionaries. Keep platform-only details in the runtime service registry only if they cannot be expressed in the routing contract. |
| Runtime behavior | One production application/handler per API route | Legacy module names are thin, tested adapters only while an external consumer exists. |
| Database state | Models + checked-in ordered migrations | Runtime models do not replace migration history; schema and OpenAPI are generated/compared, not independently handwritten where avoidable. |
| Configuration and identity aliases | One canonical environment-name mapping | Aliases have owners, removal conditions, tests, and a sunset; consumers do not each invent fallback names. Never store secret values here. |
| Tests and CI commands | One checked-in test/lint/build command per deployable subsystem | PR, nightly, release and manual CI invoke the shared commands with scoped tests, rather than keeping their own mutable copies of a test list. |
| Agent/developer policy | Root `AGENTS.md` and scoped overrides only | `.agents` skills and docs add execution details but must not redefine the constitutional invariant. Keep exception rationale next to the exception. |
| Human docs | `docs/INDEX.md` + short architecture map + operational runbooks | Generated links/tables point to live paths; mark old material historical instead of keeping competing plans as current. |

**Important decision:** `config/service_registry.yaml` and `core/config/service_topology.yaml` are not automatically interchangeable. The former contains Render service identity, resource estimates, runtime/health/environment and watch paths; the latter models multi-platform routing, exclusions, noise and manual-only services. The single-source outcome may be one richer YAML registry with distinct `runtime` and `routing` sections, or a small registry plus a generated routing projection. Pick the smallest representation that preserves real differences; do not collapse meaningful schemas merely to have one file.

### 3.2 Quality bar for every change
1. State the user-facing or operator-facing behavior being improved and its current evidence.
2. Trace the actual entrypoint and every production consumer. Name the owner of the replacement before removing the old path.
3. Fix the cause at the authoritative owner. No catch-all fallback that converts required-feature failure into a healthy process; optional features must be explicitly optional, logged, visible in health/status, and tested.
4. Prefer a small pure function, existing helper, standard library or declared dependency over a framework, new service, speculative abstraction, duplicated registry, or generic policy layer.
5. Add the smallest direct regression test that proves the former failure and the corrected contract. Preserve security negative tests and data migration/backward compatibility proofs.
6. Add a code comment for a deliberate exception or second implementation, stating why it must exist, the distinct owner/use case, and the removal trigger. Do not add narration comments for obvious code.
7. Measure before claiming fastest/lightest/free: cold start, p50/p95 latency, RSS, image/install size, API/provider cost, cloud build/test minutes, failure rates, and local-vs-CI reproducibility. Prefer free/local options, but do not describe unpaid quotas, third-party services, or credentialed browser sessions as guaranteed zero-cost or zero-risk.
8. No blanket line-budget rules, deleting tests/docs based on count, `except Exception: pass`, relaxed gates, quiet skips, or compatibility shims without a named consumer and end date.

### 3.3 Proposed measurable service objectives (agree before gating)

These are **targets to baseline**, not current verified guarantees:

- PR required checks: fastest deterministic safety/syntax/schema checks first; changed-subsystem behavior checks next; broader integration/nightly suite later. Pin a warm-run and cold-run latency budget per job and publish the measured baseline.
- No test skipped because an import/feature failed silently. Each skip has an owner, reason, condition and expiry/re-enable issue; tests for retired behavior are removed only with product approval.
- Every supported service has one verified build command, health/readiness contract, release identity and deploy selector; a changed unrelated path causes no service build/deploy.
- Every credential-bearing endpoint/tool has auth/authorization, tenant-boundary, abuse/rate-limit and redaction tests; zero secrets in git and logs.
- Runtime resource/cost budgets are taken from observed deployment traces and provider billing/quota, not asserted as measured based only on comments.

## 5. Prioritized execution sequence
Deliver each as a separately reviewable, reversible change. The order intentionally fixes broken evidence and canonical routing before deleting broad code.

### Phase 0 — Capture reproducible baseline and resolve known failures (first)

1. Pin the target SHA and record tool versions; add a clean Windows + Linux validation baseline.
2. Fix the default service-topology config path and add a test calling `detect_deploy_targets.py` without `--topology` for real checked-in fixtures.
3. Resolve the four focused pytest failures by tracing their contracts: empty core/gateway parity expectation, `core/browser` duplicate invariant vs. tracked implementation, docs link/fragment drift, and Windows UTF-8 handling. Correct the rule or the implementation with a direct rationale; do not lower thresholds just to pass.
4. Register the intentional pytest markers (including `unit`) and enable unknown-marker failure after fixing current callers.
5. Capture `collect-only` time, scoped suite wall time, full-suite time, image build size, production image install dependencies, service RAM/startup/latency, and CI/cloud usage. Do not set arbitrary budgets before collecting a representative sample.

**Exit:** targeted wiring/schema/import/deploy/doc regression pack passes on Windows and Linux; baseline records actual state, skips and resource/cost numbers.

### Phase 1 — Decide product surface and topology
1. Make a reviewed one-page list of actual production services, actual public APIs, actual browser/session mode, MCP transports, user-facing clients, data stores and active deployment integrations.
2. For each list `owner, runtime entrypoint, canonical config, live consumers, CI command, deploy trigger, health contract, credentials, user value`. Label every component `active`, `library`, `example`, `experimental`, `historical`, or `retired` with evidence and an owner.
3. Resolve contradictory satellite/studio/federation and Vercel/Cloudflare statements against real GitHub organization repository settings, provider resources, DNS, workflows and last deployment. Local source cannot verify the remote state.
4. Choose one deployed Gateway implementation, one service/deployment config model, one test command per product and a real role for the root VS Code package/example.
5. Classify each existing policy/check by invariant and owner; merge identical checks only where they share the same boundary. Remove duplicate enforcement only after the canonical gate proves the invariant.

**Exit:** reviewed topology decision record and machine-readable service/product inventory. No source paths are removed in this phase.

### Phase 2 — Make canonical runtime and config wiring executable
1. Fix topology discovery; route all service selectors through the chosen canonical registry/adapter. Keep distinct platform deployment metadata where appropriate.
2. Have one contract checker validate the registry against `render.yaml`, Docker build contexts/entrypoints, health endpoints, GitHub deploy keys, and test fixtures.
3. Consolidate route/app startup and router registration only after inventorying mounted paths and optional/critical modules.
4. Choose an authoritative dependency manifest per image and CI job, generate locks from it, and stop installing tooling/browser extras into unrelated services.
5. Correct deployment paths/commands and environment-config documentation against actual `rootDir` and clean builds.

**Exit:** representative changed-path matrix and clean service builds pass; absent required config fails clearly; unrelated changes cause no deploy; auth/API contracts unchanged unless intentionally versioned.

### Phase 3 — Remove dead/duplicate work in small batches
For each directory or code path: gather import/call/workflow/doc/test and runtime/log references; remove one owner or one unit at a time; run targeted tests; keep/deprecate consumer adapters with a specific expiry; observe release. Prioritize:

1. Two gateway apps and dead/duplicate route/config helpers.
2. Duplicate service watch-path/identity tables and redundant wiring scanner logic.
3. Overlapping `core/browser`, browser runtime/session helpers, core/gateway mirrors, and APIs—only when the test that exposed the mismatch has an intentional final contract.
4. Redundant memory, state, task/agent registry and provider-failover implementations.
5. Repeated test lists and stale scripts/workflow paths in CI/ops.
6. Unused dynamic skills/examples, stale docs/prompts, optional and unconsumed dependencies.

Do not combine large unrelated deletions. Retain abstract interfaces and compatibility code only where multiple true implementations or external consumers are demonstrated.

**Exit:** every removal has verified zero active consumer or migrated consumer, focused regression tests, a small diff, owner confirmation and rollback/deprecation rationale.

### Phase 4 — Security, production truth and cost/performance
1. Run security threat tests and secret/dependency/SBOM checks on the actual deployed images, plus public API/tenant boundary checks.
2. Verify real service identity/startup/readiness/degraded status and shut down cleanly on SIGTERM.
3. Measure browser SSRF/injection/session/retention controls, memory peaks, provider fallback and streaming in bounded load tests.
4. Compare CPU/RAM/startup/latency, dependency/image size, test time and external/cloud spend to the Phase 0 baseline. Optimize only measured bottlenecks; do not pursue a smaller source tree at the cost of an actual user feature or protective invariant.
5. Test deploy/rollback for each service in an explicitly authorized staging/sandbox before production.

**Exit:** no P0/P1 security or correctness defect; documented and tested health/error behavior; improvements have before/after evidence; operational rollback and incident ownership exist.

### Phase 5 — Keep the tree simple
- A change adding a second source of truth, service, package, test framework, workflow, fallback, background monitor, async queue, policy rule or abstraction must include an adjacent comment/ADR explaining the distinct requirement, cost, owner, and retirement trigger.
- Quarterly, remove only proven unowned, unreferenced, unused and unverified surfaces. Do not auto-delete by age, file size, name, generated status or lack of current test.
- Keep a one-page scorecard in the active docs: current runtime entrypoints, canonical registries/contracts, PR checks, deploy selectors, known deprecated paths and measured baseline. Link to detail instead of copying it.

## 8. What not to do
- Do not rename/split `core/` based on file count alone or build a new platform/monorepo framework.
- Do not make already-large suites larger with another census, census-of-census, shadow parser, AI evaluator or CI job when an existing exact regression can be fixed.
- Do not bulk delete scripts, agents, prompts, tests, workflows, migrations, examples or docs without owner and reference evidence.
- Do not merge Python package trees across genuinely isolated deployable products merely to deduplicate a few lines.
- Do not loosen authorization, secret checks, error visibility, migration safety, prompt-injection defense, or test assertions because they block cleanup.
- Do not call third-party model usage, hosted databases, stealth/session access, “free” plans or CI runners zero-cost/reliable without current quota, policy and usage evidence.
- Do not invent abstraction layers, generic policy engines, enterprise framework migrations, microservices or cross-platform package systems unless a measured current product limitation requires them.
