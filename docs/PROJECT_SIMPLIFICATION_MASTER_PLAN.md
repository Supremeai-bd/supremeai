## ১. সিদ্ধান্তের সারাংশ

**প্রথমে যেটা build ও run হয়, সেটাকে সত্যি যাচাই করুন। তারপর একই কাজের একাধিক implementation কমান। সবশেষে ব্যবহারহীন অংশ অবসর দিন।** এখনই বড় rewrite, নতুন orchestration framework বা সব service এক করার প্রয়োজন নেই। সবচেয়ে ব্যয়বহুল জটিলতা হলো runtime, test, docs ও deploy-এর একে অপরের থেকে আলাদা বাস্তবতা।

- **সবার আগে রক্ষা করুন:** key ও quota-সহ chat/model API (streaming এবং non-streaming), ব্যবহারকারী ও tenant-এর data boundary, সত্যিকারের task execution ও ফলাফল, permission-সহ MCP tool calls, এবং যাচাইযোগ্য deploy/rollback।
- **আগে মেরামত করুন:** deployed Gateway-এর সঙ্গে test entrypoint-এর অমিল, কাজ না করেও Worker-এর `completed`, Gateway-এর deploy input বাদ পড়া, Browser image-এর ঘোষিত বনাম উপলব্ধ capability, আর Tower-এর লাল tool-annotation check।
- **তারপর কমান:** Gateway/Core-এর সমান্তরাল route tree, একই policy-র একাধিক কপি, `scripts/` ও `scripts/ops/`-এর mirror, এবং retired UI/satellite ধরে রাখা default build ও docs। Compatible client আছে কি না যাচাই না করে route, tool বা alias মুছবেন না।
- **পরীক্ষামূলক অংশ default নয়:** Kaggle shadow, HF Tiny Brain, নতুন routing heuristic, এবং বিশেষায়িত capability-র জন্য নামযুক্ত owner, অনুমোদিত data/provider, খরচের সীমা ও measurable benefit দরকার। নিয়মিত কাজে না লাগলে আলাদা experiment রাখুন বা অবসর দিন।

## ৩. লক্ষ্য-আর্কিটেকচার: যত কম boundary-তে কাজটি নিরাপদে হয়

```text
ব্যবহারকারী / SDK ──▶ Gateway (public API, key/scopes, quota, provider transport)
ব্যবহারকারী / Admin ─▶ Core (tenant data, product workflow, decisions, approvals)
MCP client ──────────▶ Tower (tools, scopes, lease/audit, product/ops adapters)
                         │
        প্রয়োজন হলে: আলাদা Worker / অনুমোদিত Browser execution / provider adapter
```

এটি **দায়িত্বের** ভাগ, বাধ্যতামূলক microservice count নয়। Gateway public protocol-এর owner; Core domain rules এবং durable user state-এর owner; Tower MCP protocol ও governance-এর owner। Gateway Core-এর private modules import করবে না—[বর্তমান import boundary](../.importlinter) রাখুন। Existing durable DB, queues, provider adapters বা isolation boundaries কেবল একই নামে আছে বলে এক করবেন না।

**ছোট অংশের সিদ্ধান্তের নিয়ম:**

| সিদ্ধান্ত | কখন নেবেন |
|---|---|
| **রাখুন** | Verified consumer, product invariant, data recovery বা safety/compliance-এর জন্য প্রয়োজন। Security/restore function-এর মূল্য traffic count দিয়ে বিচার হবে না। |
| **সরল করুন** | ব্যবহার আছে, কিন্তু same effect পেতে অপ্রয়োজনীয় step, fallback, wrapper, flag বা network hop আছে। ছোট contract test দিয়ে outcome ধরে রাখুন। |
| **একত্র করুন** | একই actor/policy/input/output, দুটি implementation এবং parity test করা সম্ভব। আগে call site বদলান; নতুন utility বানাতে হলে পুরোনো কপি সরানোর পরিকল্পনা একই PR-এ দিন। |
| **আলাদা রাখুন** | কাজটি experiment, optional dependency, heavy workload বা ভিন্ন trust boundary-তে পড়ে। Default path থেকে আলাদা করুন; owner ও sunset date লিখুন। |
| **অবসর দিন** | Runtime/build/test/docs/packaging/cron/dynamic import-এ প্রয়োজন নেই; external consumers ও runbook review সম্পন্ন; compatibility window পার; recover/rollback সম্ভব। **Unknown ≠ unused।** |

প্রতি বদলানো file/route/tool/flag/job/adapter-এর জন্য existing PR-এই এক সারি যথেষ্ট: **`path বা symbol | caller/contract | owner | keep/simplify/merge/isolate/retire | test | rollback`**। নতুন tracking service বা নতুন architecture council নয়। সাধারণ function দিয়ে সম্ভব হলে registry/factory বানাবেন না; একটি অন্য জায়গায় call করার জন্য অপ্রয়োজনীয় proxy/API নয়। একই error-এ nested retries নয়; slow/failing dependency-তে bounded deadline ও সৎ degraded response।

সময়সূচি milestone-ভিত্তিক। Live inventory, approval ও deprecation window জানা না পর্যন্ত সপ্তাহ বা deletion target প্রতিশ্রুতি নয়। যেসব PR একে অপরের files/contracts ছোঁয় না, সেগুলি একই wave-এ চলতে পারে।

| Wave | প্রথম deliverable | পরের Wave-এ যাওয়ার gate |
|---|---|---|
| **০ · Baseline ও guardrails** | বর্তমান checkout-এ verified route/tool/job list ও red checks নথিভুক্ত; অনুমোদিত read-only ops evidence-এ deployed SHA, configured service, consumer, metrics ও branch required checks মিলিয়ে নিন। যে user journey রাখতে হবে তার তালিকা existing inventory/PR-এ। নতুন default features প্রয়োজন না হলে অপেক্ষা। | সব critical surface-এর owner, support status, measured/unknown baseline, reproducible smoke ও rollback owner আছে। Unknown surface delete list-এ নয়। |
| **১ · সত্যি কাজ করা artifact (F1–F7)** | Gateway parity, Worker result, deploy planner regression, Browser scope ও MCP metadata পৃথক ছোট PR। Provider/schema ও concrete test drift সংশোধন। Green check কোন artifact/run-কে certify করে স্পষ্ট। | সংশ্লিষ্ট deploy artifact-এ chat, authorized tool ও real task result যাচাই; deploy matrix fixtures pass; required negative tests, intentional degraded state, release/rollback evidence। Red/skipped check নীরবে বাদ নয়। |
| **২ · Hot path সরল (F8)** | Gateway-এর এক app/route owner; Core-এর এক task path per capability; config/secret precedence, tenant ও retry policy align। Tower tool handler ও registry থেকে code copy কমান। প্রথম script mirror pair; successful benchmark-এর আগে অন্য সব copy migrate নয়। | Public/auth/tenant/schema parity, same-workload latency/error/cost comparison, fallback ও old aliases test। প্রতি slice-এ একটি দ্বিতীয় implementation বা unnecessary hop সত্যিই কমেছে। |
| **৩ · Safe retirement (F8–F9)** | Dormant client/workflow, unused aliases/wrappers, experimental/default wiring ও docs review। প্রথমে deprecation/warning, then remove; runtime image slim করার পরে dependency lock regenerate। | Caller/usage review শেষ; compatibility window এবং policy approvals complete; data restore/last-good artifact জানা; all actual required checks green। |
| **৪ · ধরে রাখুন** | PR-এ one-in/one-out নয়, **new complexity-এর justification**: user outcome, কেন সরাসরি করা যায়নি, test ও operation cost। পুরোনো PR/run receipts ছাড়া নতুন governance layer নয়। | মাসে/প্রতি release-এ metrics এবং unused flag/alias review existing maintainer cadence-এ; শুধু LOC নামানো success নয়। |

## ৬. সফলতা মাপার পদ্ধতি

প্রথম wave-এ একই workload, একই provider class ও একই test data দিয়ে baseline নিন। সংখ্যা না পাওয়া মানে `unknown`, শূন্য নয়। Sample size/window সহ রিপোর্ট; প্রস্তাবিত gate incumbent contract বা SLO-কে দুর্বল করতে পারবে না।

| Metric / guard | প্রস্তাবিত acceptance |
|---|---|
| Product journeys | Supported critical flow-এর **১০০%** সংশ্লিষ্ট deploy artifact-এ positive ও relevant negative test। Chat-এর stream/non-stream, model list, auth/quota, task receipt, admin/MCP permission এবং staging rollback অন্তর্ভুক্ত। |
| Reliability ও performance | p95 first-token/total latency, error/timeout rate, tool/task completion rate, queue lag, retry/fallback rate ও cost per *successful* request আগের measured baseline-এর চেয়ে খারাপ নয়—reviewed trade-off ছাড়া। Cheap route বেছে degraded quality বা ambiguous usage নয়। |
| Data/security | Zero known cross-tenant access, unapproved mutation, plaintext secret/log leak, fake success, বা silent missed migration। Deny-case test ও backup/restore evidence অপরিবর্তিত বা শক্তিশালী। |
| Complexity ও ops | এক behavior-এর competing implementation কমেছে, replacement-এর পরে net owner/entrypoint/flag কমেছে; একই operation-এর docs ও settings এক owner থেকে। Scoped docs/test-only change-এ unnecessary release নেই। Median CI time, duplicate jobs, cold-start/RSS, image size ও cloud/API calls baseline বনাম after দেখান। |
| Release truth | `intended SHA = deployed SHA = runtime SHA` যথাস্থানে; application capability এবং DB/schema verified; runner `not run` ও unconfigured provider-কে pass নয়। [Root release gate](operations/root-release-gate.md) ও [PR lifecycle](PR_TO_PRODUCTION_LIFECYCLE.md) অনুযায়ী sign-off। |
